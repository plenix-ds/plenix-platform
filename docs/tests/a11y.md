# a11y

This test keeps every Plenix page usable for people who rely on screen readers, keyboards and other assistive tools, by scanning for known accessibility mistakes.

- File: `tests/a11y.test.js`

## What it checks
- Every application page (Dashboard, Projects, Messages, Contacts, Calendar, Tasks, Notes, Bookmarks, Files, Settings) and the Asset Manager pages (main page, system settings, my account, image editor).
- The extra settings screens: Account, Appearance, Categories, the data model docs, Users, Permissions and Preferences.
- Every page of the St. John the Beloved test site.
- On each page it runs axe-core (a standard accessibility scanner) with the WCAG 2.2 Level A and AA rules (WCAG: the Web Content Accessibility Guidelines).
- It counts, for each page and each rule, how many elements break the rule.
- It fails only when a rule is new on a page, or hits more elements than the recorded list allows. Known issues can only go down.

## Why it exists
- The scan was added in commit 4e8d647f "Versioning rules, changelog, and checks on every push (roadmap items 5 and 6)", then with a baseline of 418 known issues.
- The pages are the St. John test site and the apps, never the design spec (owner, 2026-10-25, in the file header).
- It runs only when the owner asks (owner, 2026-10-25: "Reserve only for as on demand test by owner and take out from the tests", in `tests/run.js` and `.github/workflows/on-demand.yml`).
- Issue #691 (audit #684) records that the known-issue list `tests/baselines/a11y.json` is now empty: no known issue is accepted.

## How it checks
- Starts the local test server and headless Chrome at 1440 by 1000 pixels.
- Opens each page, waits for it to settle, loads axe-core from `node_modules/axe-core/axe.min.js` and runs it with the tags wcag2a, wcag2aa, wcag21a, wcag21aa and wcag22aa.
- Compares the counts with `tests/baselines/a11y.json` (page, then rule, then number of elements). The file is `{}` today.
- `--update` rewrites the baseline, only from a full run, and only if no count grew.
- It does not use `tests/a11y-report.js`. That file is a separate work list (not a test) that groups every axe finding by rule and element; changed mode ignores it.

## What a failure means
- A page gained an accessibility problem: for example a button with no name, text with too little contrast, a missing label, or a broken list or table structure.
- A person using a screen reader or a keyboard could miss content or be unable to use a control on that page.

## When it runs
- ON_DEMAND in `tests/run.js`: only when the owner starts it (GitHub Actions > On-demand tests, the "accessibility" job, or `node tests/run.js a11y`, or `npm run test:a11y`).
- It never runs on a push, a pull request or in the full suite.
- In the on-demand workflow the owner picks the scope: "full" (every page) or "changed" (only the pages of what changed, `tests/changed.js`).

## What it needs
- Headless Chrome (CHROME_PATH) and the local test server (`tests/lib.js`).
- The St. John test site checkout (`tests/site.js`, SITE_DIR), with its database (in-process by default; the workflow gives it a PostgreSQL 16).
- axe-core from `node_modules`.
- The baseline file `tests/baselines/a11y.json`.
