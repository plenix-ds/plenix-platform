Claude Code server: the plan

One server on our own Proxmox runs the Plenix agents. You reach it from the desktop app and from your phone. Nothing runs in Anthropic's cloud: the agents, the code and the memory stay on our machine. The agents still talk to Claude through your Claude account, as they do today.

Plenix work stays on this Windows VM until you say to move it.

Built so far (2026-10-26)

  • Server: VM 131 "cc-server" at 10.0.0.32 is running. Nightly backup at 02:00 to the new "backup-store" area; a test backup worked.
  • Sign-ins: Claude (your Max account) and GitHub (account LighthouseCollection, through the browser, so it can reach all your repositories; a narrower token can replace it).
  • Repositories: cloned, with the builders' worktrees. The build, the system check and the spec check pass on the server.
  • Claude Code: 2.1.308, Anthropic's "stable" release, pinned (Opus 5.5 needs it).
  • The team: all five agents run in tmux with Remote Control on, in standby. Messaging between them works both ways. The Lead can read your answer records.
  • Guard: every session on the server runs a check before each command. Only the Lead can merge (also through the GitHub API), release, deploy or push to a main branch; nobody can force-push a main branch; no agent can write an answer record; only the Owner desk can write to the status page. Tested live.
  • The guard is a check, not a wall: an agent determined to get around it could. GitHub's own branch protection would be the hard stop; that is a GitHub setting for you to decide.
  • Files: the server's team files are in server/ beside this page.

claude-mem: installed

  • Version: 14.0.1 (17 October), installed from a checked copy on the server, so it never changes by itself. Its code was read before installing.
  • Turned off: its usage reporting (analytics), its cloud sync, and its add-on search engine (which would download more software).
  • Secrets: hiding of tokens and passwords is on, with extra patterns for Plenix's own (DS_TOKEN, Authentik, database passwords). Commands that print secrets (reading .env files, showing tokens, keys) are not recorded. Tested: a fake token was stored as "redacted" and appears nowhere in its files.
  • Where it lives: only on the server (~/.claude-mem), reachable only from the server itself. Raw command output is kept 30 days; the summaries are kept.
  • Cost: it writes its summaries with Claude Haiku, the cheapest model, on your Max plan. Every agent action adds a small Haiku call.
  • Tested: it recorded a decision, and a fresh session recalled it without reading any files.

headroom: tested, not turned on

  • Version: 0.41.0 (14 October). Its code was read first.
  • What it sends where: it sits between Claude Code and Anthropic and forwards to Anthropic only. By default it also sends anonymous usage summaries to its makers, checks for updates daily, reads your Claude sign-in to watch your plan's usage, and keeps the uncompressed output on disk for 30 minutes. All of that was turned off for the test. Compression itself runs on the server; no content goes elsewhere.
  • The catch: it only works by standing between Claude Code and Anthropic, which turns off Remote Control for that agent. There is no mode that keeps Remote Control.
  • The test: a 2,000-line test log with six important details hidden in it, read by a test agent in eight parts, three times without headroom and three times with it (both its modes).

Moving your memory into claude-mem (when you say the work moves)

  • Until then the files on the Windows VM stay the master copy; nothing is moved yet.
  • Memory files (84 files, about 420 KB): copied to the server, checked for anything secret-looking, then loaded with claude-mem's own import (one memory per file, project "plenix"). A trial run first shows what would be stored.
  • The Owner desk's decisions log (85 lines): each decision becomes its own memory, tagged as a decision with its date and issue number, so any agent finds it by searching.
  • Approvals stay where they are: your taps on the status page remain the only approval record. The memory only helps agents remember what was decided; it never counts as an approval.
  • Slim start-up: after the import, the memory index the agents read at start shrinks to about 25 lines (who you are, the rules that apply to every change); everything else comes back from claude-mem only when it matters.
  • One memory: Claude Code's own automatic memory notes are switched off on the server, so claude-mem is the only memory.
  • After the move the Windows copies are kept as a read-only backup.

The VM

  • Host: the one Proxmox node, pve (10.0.0.50). Its CPU is an AMD Ryzen 9 9900X, so the faulty Intel i9 in your PC is not involved.
  • Name and ID: VM 131, "cc-server", beside VM 130 Plenix.
  • System: Ubuntu 24.04 LTS (cloud image), updated automatically for security fixes.
  • CPU: 8 cores.
  • Memory: 16 GB. The host has 123 GB and about 28 GB free today, so this leaves about 12 GB spare. If the host gets tight, stopping VM 112 or 107 when unused helps.
  • Disk: 120 GB on the Storage pool (it has about 1 TB free).
  • Address: 10.0.0.32 (fixed), gateway 10.0.0.1. Claude checks the address is unused just before creating the VM.
  • Starts on boot: yes.
  • Firewall: SSH only, from the home network (10.0.0.0/22), key-only. Nothing is reachable from the internet.

How you reach it

  • The agents, from anywhere: Remote Control. Each agent runs with Remote Control on, under its own name ("Plenix · Lead" and so on). It shows up in the Claude app on your phone, at claude.ai/code and in the desktop app's session list. The server only makes outgoing connections, so nothing is opened to the internet. As today, the conversation text passes through your Claude account.
  • Desktop app over SSH: an SSH connection in the desktop app to cc@10.0.0.32, for starting an extra session on the server or looking at its files. These are new sessions; the standing agents are opened through Remote Control.
  • tmux: every agent runs in its own tmux window, so it keeps working when you close the app or lose the connection. One command (team) starts or shows them all.
  • Sign-in renewals: the Claude sign-in expires now and then (Claude warns three days ahead). When it does, you sign in again on the server; the agents stop until then.

What gets installed

  • Google Chrome, for the tests. Both repositories test with Chrome (through puppeteer), so Playwright's browser is not needed.
  • Claude Code, at one fixed version (2.1.229); updates happen when the Lead chooses, not by themselves.
  • Two users: ccadmin (setup, can use sudo) and cc (runs the agents, no sudo, not in the Docker group).

The repositories

  • plenix-ds/st-john-test-site, in ~/work/st-john-test-site.
  • Each builder gets its own worktree (~/work/plenix-b1, ~/work/plenix-b2), so their builds and tests never mix.

Secrets

  • You type every password and token yourself, in the server's terminal. Claude never sees or copies them.
  • GitHub: one fine-grained token for the three repositories only: code, pull requests and issues (read and write), workflows read. No admin, no delete, no other repositories.
  • Claude: you sign in with your Claude account (the normal sign-in, which Remote Control needs; not a long-lived token).
  • Tokens live in the tools' own protected files on the server (readable by cc only). They never go into a repository, a memory, a log or a message.
  • The memory system is set to skip anything that looks like a token, password or key.

Backups

  • Today there are no Proxmox backups at all, and the only backup area (local) has about 65 GB free.
  • Plan: a 300 GB backup area on the Storage pool, and a nightly backup of VM 131 at 02:00 that keeps the last 3 nights and 2 weeks.
  • The code itself is safe on GitHub; the backup protects the server's setup and its memory database.
  • These backups sit on the same machine. They protect against a bad change, not a broken disk. A second place (a NAS or Proxmox Backup Server) can come later.
  • VM 130 Plenix, Nginx Proxy Manager and Authentik are not part of this step; you said server backups are a separate matter.

Your approvals: one tap, recorded once

  • The Owner desk only adds the question to the status page. You answer by tapping a button there. Your tap saves the record in the page's database (collection "answers", one record per decision, for example issue-259).
  • No agent ever writes an answer for you. A record an agent wrote would look like yours, so a check on the server refuses any agent write to "answers". Only the Owner desk may write to the page at all (to add questions); the other agents can only read it.
  • The page is private to your account.
  • Before any merge or release, the Lead reads the record itself and checks its time and that it names that exact change. No record, no merge.
  • An answer typed in the Owner desk chat is turned into a question card for you to tap; the chat alone is not enough.
  • Messages that say "the owner approved" no longer count for anything. This is what makes approvals travel without being asked twice.

Faster start-up

  • Today every session reads about 23 KB before it starts (CLAUDE.md 9 KB, the memory index 14 KB).
  • On the server: a short CLAUDE.md (the rules that apply to every change, about 2 KB) that points to longer pages to read only when needed.
  • A slim memory index (about 25 lines); the rest moves into the memory system below and comes back only when it matters.
  • Each agent's role file holds only what that role needs.
