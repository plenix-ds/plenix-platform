The design spec now runs on the published CDN

You asked: "make the design spec a consumer of the cdn." The spec now loads Plenix from https://design-system.lighthouseway.org/cdn/<version>/, the same files any outside application uses. It no longer loads the repository's own build (../platform.css, ../dist/platform.js and the rest).

What changed

  • One setting: platform/design-system/plenix-source.js holds the version (today 0.71.0). Every spec page, lab, preview frame and source viewer asks it where Plenix is. Nothing else in the spec names a Platform path any more.
  • From the release: the stylesheet (plenix.css), the bundle (plenix.js), React, the fonts, the theme script and the icons.
  • Source files, also from the release: each spec page shows a component's real JSX, CSS, classes and tokens, which it reads as text. The CDN did not carry those files, so each release now also publishes a source/ folder, laid out like the repository (about 15 MB per release).
  • Guards: check-spec.js has a new rule (cdn): the spec's version must equal package.json's, and no spec file may load a Platform file from the checkout. deploy.sh stops if the version differs. VERSIONING.md, step 2, now says to set it at each release.

Which version: pinned, moved at each release

  • Pinned, not "latest". The spec describes one release, so it runs on that release. If it always took the newest release, a bad release could break the spec with no spec change, and pages written for one release could run against another.
  • Faster. A versioned CDN folder never changes, so browsers keep it for a year. "Latest" would need an extra lookup before anything loads (the CDN has no /cdn/latest address).
  • Same rule as the apps. deploy.sh already moves the apps to package.json's version. The spec now follows the same version.

How to preview unreleased Platform work

  • Add ?plenix=local to the spec's address, for example http://localhost:8767/Plenix/platform/design-system/?plenix=local. The spec then uses this checkout's files, as before. Run node build-app.js first.
  • ?plenix=0.70.1 opens the spec on another published release (useful for comparing two releases).
  • To keep "local" without typing the flag, run localStorage.setItem('plenix.source', 'local') once in the page's console. Remove it to go back.
  • React's development build (?react=dev) is not on the CDN, so it works only together with ?plenix=local.

What I checked

  • The CDN answers every request with CORS open to any site (Access-Control-Allow-Origin: *) and caches each version for a year. Fonts, icons, React, plenix.css and plenix.js are all there for 0.71.0. On the live site the spec and /cdn/ share one address, so nothing there loads cross-site at all.
  • Against today's real CDN (0.71.0), the spec makes 203 CDN requests and none to the checkout. Only the source/ files are missing (see the first risk).
  • Against a release built with this change (served locally), 18 pages (Color, Density, Radius, Icon, Icon inventory, Brand, Motion, Breakpoints, Themes, Button, Thumbnail, Preview, DataGrid, Testing, Use of color, Focus order, Document viewer) show the same text as with ?plenix=local. Nothing failed to load, and nothing came from the checkout.
  • check-spec.js: SPEC_OK (1173 leaves, 689 records) with the new cdn rule. build-app.js and build-packages.js run cleanly.

Risks and gaps

  • 0.71.0 has no source/ folder. On 0.71.0 the spec draws every component, but the panels that read source (JSX, CSS, classes, tokens) stay empty. Everything works from the first release built with this change. So merge both PRs and cut the next release together, or preview with ?plenix=local until then. The live site changes only when deploy.sh runs, and deploy.sh publishes the new CDN folder before the spec.
  • Tests that open the spec. About 20 tests open spec pages. Without ?plenix=local they would check the published release, not the change under test. The St. John test-site session is moving tests off the spec. Merge that first, or have the remaining spec tests add ?plenix=local. tests/ was not touched here.
  • The source is public (decided, owner 2026-10-25). /cdn/ is outside Authentik, so each release's JSX and CSS source can be read by anyone, like the compiled forms (plenix.js, plenix.esm.js, plenix.css) already were. This has no effect on GitHub access or CI, which build from the repository.
  • Many requests in the labs. The Radius, Motion and Layout labs read platform.css and its roughly 200 imported files, as they do on the live site today. deploy.sh notes that the server limits request bursts (429) for study pages. If /cdn/ has the same limit, those labs could show partial counts. This is not new, but it now applies to /cdn/.
  • Not Platform, so not moved: the sample pictures from the Asset Manager (../../dam/assets/), one Asset Manager history note, and the links to the suite's apps still come from the server next to the spec.
  • Each release now has two steps: moving the version means a spec commit and a move of its pointer. check-spec and deploy.sh refuse a mismatch, so this step cannot be skipped by mistake.

Merge order: the St. John test move, then the plenix-design-system PR and the plenix-platform PR together (the integrator moves the pointer and writes the changelog entry), then the next release. Nothing has been merged or released.
