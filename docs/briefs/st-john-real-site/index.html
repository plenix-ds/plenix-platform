St. John the Beloved as a real website: the plan

You asked for the test site to be an actual website with a real database on your server, kept out of the design spec, with its own address. This page is the plan only. Nothing on the server is built or changed until you say go.

Your four points, answered

  • 1. A real website with PostgreSQL on the server: yes. A small app and a PostgreSQL database, each in a Docker container on the Plenix server (the publish host), next to the services already there.
  • 2. Loads Plenix the way any outside app does: from the CDN, so the tests check exactly what other projects get.
  • 3. Not in the design spec: it has its own repository and no ties to the spec. It is not in the spec today either; it sits in the Plenix repository's test-site folder on the PR #345 branch.
  • 4. The address: today it is local only, at http://localhost:8767/Plenix/test-site/index.html once #345 is merged. The proposed web address is https://stjohn.lighthouseway.org.

How it fits together

  • The pages: the 35 pages built in #345, unchanged in look. Today they read made-up data from a file; after this they ask the app for it, and the app reads PostgreSQL.
  • The app: Node 22 with one library, the PostgreSQL driver. It serves the pages and a small JSON API (/api/members, /api/families, /api/events, /api/gifts, and so on). Changes are saved: a new member, a sign-up or a pledge stays in the database.
  • The database: PostgreSQL 16. The tables are members, families, households, ministries, services, feasts, events, RSVPs, servants and sign-ups, funds, gifts, pledges, announcements, documents and media.
  • No sacrament records: there is no table for them, so they can't be stored, even by mistake.
  • Plenix: loaded from design-system.lighthouseway.org/cdn/<version>/, the same four files every outside app uses. The version is one setting.
  • On the server: two containers (st-john-app and st-john-db), the server's Nginx in front, and Nginx Proxy Manager for HTTPS, the same way plenix and design-system are set up.

Which Plenix version the tests check

  • The site has one setting, the Plenix address. The live site uses the version it is pinned to. Tests can point it at any other version without changing the site.
  • A test that finds a problem on a released version shows exactly what an outside app would see.

Made-up data, seeded and reset

  • Migrations: numbered SQL files (001-people.sql, 002-worship.sql, …), applied in order by a short script that records which have run.
  • Seed: the same fixed generator as today: 120 families, about 400 members and 10,000 gifts, the same on every load, so the tests always see the same data.
  • Reset: the live site goes back to the seed every night (and on request), so a visitor's changes never pile up. Tests start from a fresh copy every run.
  • Backups: none needed. Everything can be made again from the seed, and you asked for no Proxmox backups.

The tests on GitHub

  • Each browser job starts a throwaway PostgreSQL next to the tests (a GitHub "service container"), runs the migrations and the seed, starts the app, and runs the tests against it.
  • This adds about a minute to each job. The full run stays around 25 minutes instead of the old 5 hours.
  • The Plenix repository reads the St. John repository with a read-only token (one secret, like the spec's DS_TOKEN). The spec is never checked out for the tests.

Putting it on the server (after your go)

Order of work

  • Now: merge #345 when you are ready. The tests leave the spec today, with the site as plain files.
  • Step 1: create the St. John repository and move the site there, loading Plenix from the CDN.
  • Step 2: add the app, the database, the migrations and the seed; the pages read the API.
  • Step 3: GitHub runs the tests against the app with a throwaway database.
  • Step 4: put it on the server at the address you choose, behind the sign-in you choose.
