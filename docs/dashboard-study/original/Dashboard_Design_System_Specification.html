DASHBOARD DESIGN SYSTEM · SPECIFICATION 1.0

Dashboard design system

The canonical specification for personal, parish-office and engineering dashboards: layout, foundations, customization, every widget, data states and implementation. Mockups are interactive and use sample content.

01 / PRINCIPLES

Principles

Ten principles govern every dashboard. “Must” and “never” are requirements. “Should” is the default that needs a reason to depart from.

IDPrincipleStandard
P1Hierarchy before stylingEvery dashboard orders content by what needs action. Fix grid and hierarchy first, then card anatomy, then rows, icons and states.
P2Purpose decides the componentMetric, queue, agenda, feed, project row, presence list and status notice are distinct components. A bordered box with a title is not a component.
P3Role decides the templatePersonal, parish and engineering dashboards share one shell, tokens and interaction rules, and differ in what comes first.
P4Trust in dataEvery number states unit, scope, period and source freshness. Missing data is never shown as a value or as zero.
P5Every state is designedLoading, empty, stale or partial, error, permission restricted and pending are specified for every widget. An error is never shown as empty.
P6One source of truthAn item shown in several places (notification, attention item, to-do row) links to one underlying entity.
P7Customization is a modeRearranging happens in an explicit Customize mode with a non-drag alternative, Undo and per-person storage.
P8Accessible by constructionWCAG 2.2 AA, keyboard completion of every task, visible focus, no information carried by color alone, reduced motion respected.
P9Platform tokensPlenix DS owns color, type, radius, spacing and icons. This specification adds no parallel style system.
P10Samples are not requirementsMockups use sample content. Conditional elements appear only when the data source provides them.
Sample content mockups use sample data Conditional element appears only when its data exists Variant an approved alternative Default the standard unless a variant is named

2.1 Container grid

The grid measures the content region, not the viewport, because the application shell has navigation. Columns follow the container: 4 below 640px, 8 from 640, 12 from 960, 16 from 1440. Information tiers

  • Attention: overdue items, failures, approvals, urgent gaps. Must be actionable without searching.
  • Performance: metrics with period and comparison. Scope is explicit.
  • Exploration: recent work, notes, contacts, history.
  • Role templates reorder the tiers: parish coverage first for the parish office, blockers first for engineering, finance KPIs first for finance.
  • Every widget declares its role, source, period, permissions, action, size and destination view.

2.4 Sizes and limits

Widths
Compact, Standard and Wide. A widget’s minimum width is set by its content, not by the grid.
Lists
A card previews 3 to 6 rows, then “View all (N)”. Nested scrolling is avoided.
Metrics
Compact tiles of about 110 to 144px.
Guideline
4 cards per row and 12 per page by default. A warning, not a block.
Mobile
One ordered column in priority order. Essential KPIs reflow into a block and never scroll sideways.

3.3 Type, color, icons, tokens

Tokens
Plenix DS owns color, type, radius, spacing and icons. Values on this page are reference values until mapped to Plenix DS tokens. A dashboard token is added only for a semantic need that no existing token covers.
Accent
Reference accent #0F6CBD until the Plenix DS accent is mapped.
Type
Page title 24, card title 14 semibold, KPI value 32/40, row text 14, metadata 12 (never below 12). Tabular numerals for counts, money and times. Monospace only for code identifiers.
Surface
Neutral canvas, white cards, 1px border, 8 to 12px radius. Elevation only for a dragged item, menus and dialogs.
Header
Title left, one relevant action right, overflow menu only for real settings. Plain muted 16px icon, no tinted tile. Subtitle only when it adds scope, such as “Next 8 days”.
Counts
Neutral or brand chip. Red is reserved for errors and overdue.
Icons
One SVG family and one stroke style. 16px inline, 20px for page-level actions. One glyph per concept. Icon-only buttons have accessible names.
Status
Icon, color and a word. Never color alone. Project colors never reuse status red.
Rows
Whole row or tile is the link. Actions appear on hover or focus and replace the timestamp. They stay visible on touch.
Motion
Minimal feedback only: a drop settling, a toast. Nothing animates for decoration. All motion stops under reduced motion.

3.4 Date, time and language

  • 12-hour clock by default. Dates follow the locale.
  • Right-to-left layout and Arabic are supported on every dashboard. Long Arabic and English strings must not break the grid.
  • Lists are sorted. Time is relative within a day (“5 min”), then clock time, then date. Overdue is a visible state.
  • Time zone is explicit wherever events or deadlines are shown.
04 / CUSTOMIZE MODE

Customize mode

Customizing is a page-level mode. View mode shows no handles, no dashed borders and no instruction text. Every change saves at once and can be undone.

To do
Calendar
Notifications
Emails
Contacts
Projects
Reference behavior: choose Customize, then drag a handle, open ⋯ for “Move to position”, drag a corner, or Tab to a handle and press Space.

Interaction

Enter
One Customize button in the page header. It becomes Done. Handles, corner grips and the ⋯ menu appear only now.
Move: menu
The ⋯ menu offers “Move to position” with the list of positions, and a Size list. This is the single-pointer alternative to dragging (WCAG 2.2 SC 2.5.7).
Move: drag
Drag from the handle only. The card lifts, its slot becomes a dashed placeholder, neighbors reflow. On touch, press and hold the handle for 300ms to lift.
Move: keyboard
Space picks up, arrows move, Enter drops, Escape cancels. A live region announces “Calendar, position 2 of 6”. Focus returns to the handle.
Resize
Drag the corner. Width snaps to Compact, Standard or Wide. Left and right arrow keys on the corner do the same.
Save
Autosave on every change. “Saved” and Undo appear. Reset to default is always available and reversible.

Rules

  • Limits: default guideline of 4 cards per row and 12 per page. A warning, not a block.
  • Storage: region, size and order with a revision number, per person and per dashboard. Never raw x and y.
  • Hide is not delete: hiding a card removes it from the page, not its records. Critical notices cannot be hidden.
  • Conflicts: if two sessions edit one layout, alert and merge or reload. Never overwrite silently.
  • Mobile: one ordered column. The ⋯ menu moves cards; long-press drag is optional.
  • Defaults: role-aware defaults may exist. Layout changes never bypass permissions.

07 / DATA, STATES AND PERMISSIONS

Data, states and permissions

7.1 Six states

StateStandard
LoadingA skeleton that matches the final shape. No fake zeros. No indefinite spinner.
EmptySays what is empty and offers the next step. Distinguishes “no data” from “no match for this filter” and from “not permitted”.
Stale or partialKeeps the last good data. Shows source, coverage and last successful update. Never mixes missing sources with current ones.
ErrorA local explanation, what remains trustworthy, and Retry. Diagnostic codes sit behind Details. Never shown as empty.
Permission restrictedNo sensitive previews, aggregates or hidden-record counts. Offers access only where the product supports it.
PendingImmediate local feedback for reversible changes, then confirmation. Roll back and explain if the server rejects it.

7.2 Behavior standards

TopicStandard
Zero and missingA zero denominator is “not scheduled”, never 100%. Missing data never becomes zero. Verified zero, stale value and unavailable look different.
One entityAn item shown as a notification, an attention item and a to-do row links to one entity and one source of truth. Duplicates collapse to one line with a pointer such as “Also in Emails”.
Drill-inOpening a KPI, task, project or chart keeps the current scope, filters and period. Back returns to the dashboard with scroll position and filters preserved.
Click targetsCheckbox, menu and contact actions are separate from row navigation. A row never triggers a nested action.
RefreshBackground updates never steal focus, move the page, or reorder the focused row. New items arrive as a “1 new” pill. Each source shows “synced X ago”.
PresenceStatus has a source and a time. Unknown is not offline. An expired status becomes “unconfirmed”.
AuthorizationRole checks apply to source queries, aggregates, previews, exports and actions, not only to what is drawn. A widget saved in a layout never bypasses permissions.
ConcurrencyTwo sessions editing one layout produce an alert and a merge or reload, never a silent overwrite.
EvidenceA chart never invents a series from a total. Chart data also exists as a table.
08 / ACCESSIBILITY AND LANGUAGE

Accessibility and language

Conformance
WCAG 2.2 level AA: contrast, visible focus, accessible names, text alternatives for charts, reduced motion.
Dragging
Everything done by dragging has a single-pointer way that does not drag (SC 2.5.7) and a keyboard way. These are separate requirements.
Keyboard
Every task completes by keyboard. Focus order follows reading order. Focus returns to the trigger after a dialog or a move.
Touch
Hit areas at least 44px. Hover actions have a visible touch equivalent.
Screen readers
Moves, saves and errors are announced once, not repeatedly. Icon-only buttons have specific names.
Color
Status never relies on color alone. Test in grayscale and high contrast.
Language
Right-to-left, long Arabic and English strings, locale dates, 12-hour clock.
Test widths
320, 375, 768, 1024, 1440 and ultrawide. 200% zoom. Lists of 100 or more rows. Long names.
09 / IMPLEMENTATION

Implementation

9.1 Sequence

Phase 1 · Meaning and standards

  • Inventory widgets, sources, periods and permissions.
  • Map Plenix DS tokens, icons and header anatomy.
  • Fix layout mode and profile per application.
  • Define states for each data source.

Phase 2 · Grid and primitives

  • Container grid and region model.
  • Card frame, row, KPI, queue, agenda, state notice.
  • Source adapters with timestamp and coverage.
  • Layout engine with Customize, Undo and storage.

Phase 3 · Widgets and roles

  • High-value widgets: tasks, agenda, notifications, projects.
  • Parish and engineering widgets.
  • Role templates built on the primitives.
  • Tests across widths, languages and roles.

9.2 Widget dossier format

Every widget is specified with the same sections: Information and presentation, Behavior, States, permissions and mobile, Variants.

9.3 Definition of done

  • Each metric names unit, scope, period and drill-in. Unavailable and zero never look the same.
  • Each widget has loading, empty, error, stale, permission and pending behavior where it applies.
  • Keyboard and touch can do the same things. Every drag has a clickable alternative.
  • No hover-only essential information. No truncated critical text without a way to read it.
  • Role checks apply to queries, counts, previews and actions.
  • Persistence survives refresh. A failed save never claims success.
  • No chart is filled with invented data.
  • Icons come from one shared Icon component, delivered as versioned files or sprites.

9.4 Validation scenarios

ScenarioMeasure
An engineer identifies a blocked decision and opens its source.Time, wrong turns, whether urgency and incomplete coverage are understood.
A parish administrator fills the next unstaffed service slot.Correct service and role, conflict awareness, successful assignment.
A personal user completes a task, joins an event and finds a collaborator.Completion without accidental navigation, date comprehension, correct channel.
A finance user compares giving periods and drills to transactions.Correct reading of period, amount and currency, and access limits.
Keyboard and touch users move Calendar ahead of Notes.Successful non-drag rearrangement, focus continuity, understanding of saved state.
