## Avoiding conflicts: Wave 0: the parts system (one writer, before any lane starts; no leaves)

inventory.js, inventory-docs.js, the *-labs.js files, ds-sample-*.css, components.tokens.json, web-native-map.json, platform/index.js and platform.css are shared by every lane. Each lane instead owns its own part files; generators flatten them, and only the integrator commits the generated results.

1. platform/design-system/parts/ (new folder). A lane owns wNNL.records.js, wNNL.labs.js, wNNL.docs.js and wNNL.css (NN = wave, L = lane A/B/C), and nothing else in the folder.
2. parts/wNNL.records.js: DSParts.records.push(function (H) { var h = H.h, P = H.P, box = H.box, row = H.row, eachV = H.eachV /* … */; return [ { id, sec, sub, leaf, plenix, src, css, covers, variantPages, examples, icon, … } ]; }); — variantPages and the icon live in the record (no edits to the ICON map, no add-pages.js into inventory.js).
3. parts/wNNL.labs.js: if (window.DS && DS.registerLab) { DS.registerLab('<record id>', spec); … } — the guard lets the Node loaders (check-spec, build-packages, build-native-guidance) read the bundle without a DOM.
4. parts/wNNL.docs.js: DSParts.docs.push({ '<record id>': { purpose, anatomy, behavior, a11y, content } });
5. parts/wNNL.css: the lab specimen frames for that lane (tokens only, no numbers), as ds-sample-<group>.css today.
6. build-spec-parts.js (repo root, new): concatenates parts/*.records.js, *.labs.js, *.docs.js in name order into platform/design-system/spec-parts.js (each part wrapped in try/catch that logs the part name), and parts/*.css into ds-sample-parts.css. Deterministic; run by build-app.js.
7. inventory.js (one edit): a HELPERS object with the closure helpers (h, P, S, W, noop, use, row, stack, box, surface, onAccent, TONES, cap, each, eachV, q, fieldStates, FIELD_STATES, OPTS, ROWS, TREE, FOPTS, header, A, C, M, F, D, m); before the defaults loop: (window.DSParts ? DSParts.records : []).forEach(function (f) { R.push.apply(R, f(HELPERS)); });
8. inventory-docs.js (one edit, at the end): (window.DSParts ? DSParts.docs : []).forEach(function (d) { Object.assign(window.DSDocs, d); });
9. index.html: <script src="spec-parts.js?v=…"> after layout-lab.js and before inventory-taxonomy.js (defines window.DSParts = {records:[], docs:[]} first); <link> ds-sample-parts.css. component-lab.js frame srcdoc: add ds-sample-parts.css to its stylesheet list.
10. check-spec.js, build-packages.js (line 196 list), build-native-guidance.js: load spec-parts.js before inventory.js.
11. Exports: each lane owns platform/exports/wNNL.js (export { X } from '../components/X/X.jsx'; …) and platform/exports/wNNL.css (@import url("../components/X/x.css"); …). build-exports.js (new) rewrites one GENERATED block in platform/index.js and one in platform/platform.css (between /* BEGIN library parts (generated) */ and /* END */ markers) as flat lines from those files, so spec.js (css from platform.css imports) and check-system (missing stylesheet) keep working unchanged.
12. Tokens: build-tokens.js and platform/tokens/build.json accept a glob set ("components/*.tokens.json", also "semantic/*.tokens.json", "reference/*.tokens.json") in name order; each new component owns platform/tokens/components/<name>.tokens.json; foundations own platform/tokens/semantic/<topic>.tokens.json. components.tokens.json itself is never edited by a lane.
13. Native map: build-native-guidance.js also reads platform/standards/web-native-map.d/*.json (each lane owns wNNL.json) and merges it with web-native-map.json, so every new web record gets its iOS/Android counterpart without a shared edit.
14. Guidance: lanes never edit inventory-guidance.js (23k lines). A record's own fields win over guidance already; the integrator runs tools/prune-guidance.js (new) once per wave to drop the keys that now have a record.
15. Census: tools/library-census.js reads plan.json and reports, per lane, which leaves are done (record or covers exists, src resolves, export public, lab registered when it has variant cards, variant pages present, native map present).
16. Packages: build-packages.js runs every build-packages.d/*.js step (one loop added here), so the wave-15 package lanes add files instead of editing build-packages.js.
17. Ports: lane A/B/C use LABS_PORT 8831/8832/8833 and their own serve ports for screenshots.
18. Generated files (spec-parts.js, ds-sample-parts.css, the index.js/platform.css blocks, token CSS, tokens.index.json, dist/*, usage.js) are rebuilt locally by any lane for testing but committed only by the integrator, from a clean worktree (parallel-sessions rule).

Integrator, per wave:

- After the three lanes of a wave report done: run build-spec-parts.js, build-exports.js, build-tokens.js, build-app.js, check-system (also with platform/design-system moved aside, for CI), check-spec, LABS_ONLY=<the wave's labs> labs.test.js, prune-guidance, census.
- Release the wave as one version (next version from the highest CHANGELOG entry; next free batch number from the work log), deploy from the clean worktree, tag, confirm CI green. The owner reviews live.

## Recipe per kind (what done means)

Reuses the Every Variant recipe (scratchpad/variants/BRIEF.md; memory plenix-variant-pages-program): tokens, an All lab with one --plx-comp-* token per value, a variant page per card, labs.test.js. Lanes edit only their own files.

### component

- platform/components/<Name>/<Name>.jsx with the standard header comment (Summary, Usage, Props, Behavior, Notes) — the spec reads overview and API from it; strings prop for every word; forwardRef where it wraps a control
- <name>.css with plx-<name> BEM classes, every value a --plx-comp-* token declared in platform/tokens/components/<name>.tokens.json (node tokenize-component.js <css> for a first pass); no raw values, no inline styles, 4px grid, focus = border color only, logical properties
- exported through platform/exports/wNNL.js + .css
- a record in parts/wNNL.records.js: canonical sec/sub/leaf, plenix, src, css, level, interaction, aliases, use, avoid, related, map (Carbon, Atlassian, Material 3, Fluent 2, Polaris, Spectrum), covers (its variant and duplicate leaves), examples, variantPages (one per variant card, name = card name)
- docs in parts/wNNL.docs.js (purpose, anatomy, behavior pointer/keyboard/focus/responsive/motion/loading/error, a11y), moved from its inventory-guidance.js entry
- a lab in parts/wNNL.labs.js (DS.registerLab: sizes, variants, states, content, props with a cat from the labs test MARK list, token(), html() with real classes and no style=)
- native counterparts in platform/standards/web-native-map.d/wNNL.json
- done = node --check, check-system, check-spec, LABS_ONLY=<id> LABS_PORT=<lane port> node tests/labs.test.js ok, one screenshot of its page light + dark

### pattern

- as component, under platform/patterns/<Name>/, composed only of Platform components (no new primitives inside a pattern; a missing primitive is its own component task first)
- the lab covers the pattern's own tokens (spacing, regions); its variant pages show the compositions
- done = as component

### extend

- edit the existing component in place: the new prop/variant documented in its header comment, its CSS on (new) component tokens, existing behavior and snapshots unchanged
- give the leaf its own record in parts/wNNL.records.js (home = the leaf, same src as the existing record) with examples and variantPages for the new variants; when the existing lab lives in a shared *-labs.js file, the lane re-registers it from its own labs part (spec-parts.js loads after every *-labs.js): DS.registerLab(id, Object.assign({}, DS.labs[id], { variants: DS.labs[id].variants.concat([...]) })), never editing the shared file
- covered-elsewhere and duplicate leaves: a thin record (home = the leaf) with plenix/src of the existing code, examples, use/avoid, related to the main record; no code change
- done = check-system, check-spec, labs test for the touched lab, screenshot

### foundation

- code in platform/system (CSS), platform/utils or platform/hooks (JS), platform/providers (context), or platform/tokens/semantic|reference/<topic>.tokens.json; exported if JS
- a rules page: a record with level Foundation, guide { render } or examples drawn with Platform components, and the rules as use/avoid
- a foundation task never edits the components that will adopt it: adoption is part of that component's extend task (or a later adoption task)
- where it is a rule, a check-system rule (check-system.rules/<name>.js, registered by the integrator) or a test
- done = check-system, check-spec, its test or rule passing, page screenshot

### template

- platform/templates/<Name>/<Name>.jsx (+ css only for region placement, on tokens) built from existing components and patterns; exported; a live demo inside its record's examples
- the 8 existing template records without code (listing-page, content-template, master-detail-workspace, single-pane-workspace, full-screen-workspace, detail-page, home-page, search-results-page) get src in the same wave
- done = check-system, check-spec, pages render at Narrow/Medium/Wide (reflow test for that page)

### package

- packages/<name>/ built by a build-packages.d/<name>.js step that build-packages.js runs for every file in build-packages.d/ (wave 0 adds that loop, so the lanes never edit build-packages.js)
- published with the release as @plenix-ds/<name>; a record in 14 Implementation with install and usage
- done = npm pack dry run, a sample app under packages/<name>/example builds
